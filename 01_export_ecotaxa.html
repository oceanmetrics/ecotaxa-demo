REST API, token login, general export job, cached locally

What this does

EcoTaxa’s REST API ({ECOTAXA_URL}/api/docs) exposes a general export job: it writes a zip with one TSV per sample (object, sample, acquisition and process fields, plus each object’s category, annotation status, annotator and date) and, optionally, the images. This notebook logs in with a token, starts the job for the project, waits for it, downloads and unzips it under data/export/, and reads the TSVs into one objects table cached as Parquet. Later notebooks read the cache and never touch the node.

The project is ECOTAXA_PROJECT_ID (default 2, the demo project; the setup below prints which one this page ran on). Credentials come from a git-ignored .Renviron (ECOTAXA_URL, ECOTAXA_USER, ECOTAXA_PASSWORD) or from ECOTAXA_TOKEN, a login token handed to the render so no password sits on the machine. An export already unzipped under data/export/ is reused unless ECOTAXA_REFRESH=1. When no login is configured on project 2, the notebook falls back to the upstream test set in data-raw/import_test/, which is the byte-identical source of project 2’s eight objects (see data-raw/README.md), so the rest of the pipeline still runs on the same data; it says so below.

prior <- file.path(DIR_EXPORT, "export.json")
reuse <- file.exists(prior) && !identical(Sys.getenv("ECOTAXA_REFRESH"), "1") &&
  grepl("^EcoTaxa API", fromJSON(prior)$source) && length(ecotaxa_export_tsvs(DIR_EXPORT)) > 0
if (reuse) {
  tsv_paths <- ecotaxa_export_tsvs(DIR_EXPORT)
  source_of_objects <- fromJSON(prior)$source
  cat("reusing the export of", fromJSON(prior)$exported_utc, "(set ECOTAXA_REFRESH=1 to export again)\n")
} else if (ecotaxa_has_login()) {
  token <- ecotaxa_login()
  # a project of a million objects with images takes the node well over the default ten minutes
  tsv_paths <- ecotaxa_export(PROJECT_ID, DIR_EXPORT, token = token, with_images = "first", timeout_s = 6 * 3600)

  source_of_objects <- "data-raw/import_test (upstream test set; no ECOTAXA_USER/ECOTAXA_PASSWORD in this session)"
}

Notes

  • The export carries object_annotation_category_id, the node’s internal taxonomy id, which notebook 02 resolves. It carries no AphiaID.
  • A login token from POST /api/login is a JWT; the API also offers /token with a refresh token, which a scheduled pipeline should prefer.
  • with_images = "first" ships the visible image per object; "all" can produce several TSV lines per object.

Lessons learned (project 4, 2026-11-10)

The first real export, of 967,734 objects, found five things the eight-object demo could not. Each is now handled in R/ecotaxa_api.R or R/taxa.R, with a test:

What happened Cause Now
422 Unprocessable Entity on starting the job split_by = "" is not in the node’s enum (sample, acquisition, taxon, none) ecotaxa_export_body() checks against the OpenAPI enums
500, relation "taxo_recast" does not exist the node’s DB was built without two tables (a node issue, not a pipeline one) fixed on the node; see 05 Migrate
the job sat at “1 % Start TSV export” forever the back end was OOM-killed (2.44 GB container) loading every row at once; the job row is never updated after that one job per batch of samples, at most max_objects (40,000) each; a job whose progress stalls for 20 min stops the run
object_annotation_category_id missing the export carries internal ids only with with_internal_ids the id is resolved from the category’s display name (unique on a node) against the project’s own categories; no match stops
every date blank downstream the export writes YYYY-MM-DD and HH:MM:SS, the import format is YYYYMMDD and HHMMSS ecotaxa_datetime() reads both

Also: download with a long timeout and unzip with the system unzip (zip64, over 4 GB); batches leave a marker under data/export/project-<id>/batches/, so a stopped run resumes after the last finished batch; each finished job is deleted on the node so its files do not fill the node’s disk. For project 4 the 28 batches took 44 minutes and gave 105 TSVs and exactly one image per object (967,734), which also removed the 6,962 byte-identical second images the backup carried.

## Lessons learned (project 4, 2026-11-10)

The first real export, of 967,734 objects, found five things the eight-object demo could not. Each is now
handled in `R/ecotaxa_api.R` or `R/taxa.R`, with a test:

| What happened | Cause | Now |
|---|---|---|
| `422 Unprocessable Entity` on starting the job | `split_by = ""` is not in the node's enum (`sample`, `acquisition`, `taxon`, `none`) | `ecotaxa_export_body()` checks against the OpenAPI enums |
| `500`, `relation "taxo_recast" does not exist` | the node's DB was built without two tables (a node issue, not a pipeline one) | fixed on the node; see [05 Migrate](05_migrate_from-ifremer.qmd) |
| the job sat at "1 % Start TSV export" forever | the back end was OOM-killed (2.44 GB container) loading every row at once; the job row is never updated after that | one job per batch of samples, at most `max_objects` (40,000) each; a job whose progress stalls for 20 min stops the run |
| `object_annotation_category_id` missing | the export carries internal ids only with `with_internal_ids` | the id is resolved from the category's display name (unique on a node) against the project's own categories; no match stops |
| every date blank downstream | the export writes `YYYY-MM-DD` and `HH:MM:SS`, the import format is `YYYYMMDD` and `HHMMSS` | `ecotaxa_datetime()` reads both |

Also: download with a long timeout and unzip with the system `unzip` (zip64, over 4 GB); batches leave a
marker under `data/export/project-<id>/batches/`, so a stopped run resumes after the last finished batch;
each finished job is deleted on the node so its files do not fill the node's disk. For project 4 the 28
batches took 44 minutes and gave 105 TSVs and exactly one image per object (967,734), which also removed the
6,962 byte-identical second images the backup carried.
